TEST DESIGN

Why boundary values are the first thing I test

On every new feature, I check the edges before the happy path — here's the exact list I run through.

⌄

When a new feature lands in my queue, it's tempting to start with the happy path — the obvious, intended use case everyone already tried in dev. I don't. I start at the edges.

Boundary values are where most real defects actually live: the first and last valid values, the values just outside the valid range, empty input, and the maximum the system is supposed to tolerate. A date picker that accepts "today" but silently breaks on the last day of a leap year. A quantity field that accepts 1–100 but lets through -1 or 101 without validation. A text field with a 255-character limit that truncates silently at 256 instead of rejecting the input.

My quick checklist for any new input or workflow:

  • Minimum valid value, and one below it
  • Maximum valid value, and one above it
  • Empty / null / missing input
  • The exact boundary of any stated limit (character count, date range, upload size)
  • Duplicate or repeated submission (double-click, back-button resubmission)
  • Values that are technically valid but operationally unusual — a $0 order, a same-day start-and-end date, a user with zero existing records

This isn't about pessimism — it's about recognizing that developers naturally test the path they just wrote, which is almost always the middle of the range. QA's job is to live at the edges on purpose. On the Availity healthcare portal, this habit alone has caught UI state bugs that only showed up with empty result sets or single-record responses — cases that never appear in a demo with realistic sample data, but happen constantly in production the first week a new clinic goes live.

BUG REPORTING

A simple triage framework for vague bug reports

"It's broken" isn't a bug report. Here are the three questions I run it through first.

⌄

Every QA engineer gets some version of "it's broken" at least once a week — from a stakeholder, a support ticket, or a teammate in passing. Before I open a defect ticket, I run it through three questions.

1. Can I reproduce it, and how reliably? If I can't reproduce it in three attempts, I don't file it as confirmed yet — I note the conditions I tried and ask the reporter for exact steps, browser, and account state. A huge number of "random" bugs turn out to be 100% reproducible once you match the right precondition: a specific user role, an empty cart, a timezone offset.

2. What's the actual vs. expected behavior, stated precisely? Not "the page is broken" but "clicking Submit with a valid form shows a blank white screen instead of the confirmation message." Precise actual/expected framing does most of the work of the ticket for you, and it's the difference between a developer fixing it in ten minutes and re-reproducing your steps from scratch.

3. What's the blast radius? One user, one browser, one edge case — or everyone, right now, on the critical path? This isn't about assigning severity labels for their own sake; it's about making sure a P1 doesn't sit behind five P3s in a queue because nobody separated them.

Once those three are answered, writing the actual ticket is almost mechanical: steps to reproduce, expected vs. actual, environment, severity, and — if I have it — a guess at where in the stack the problem likely lives. That last part isn't required, but it's the fastest way to earn a developer's trust that your reports are worth opening first.

API TESTING

My API testing checklist before I call an endpoint "tested"

A 200 response isn't a pass. Auth, pagination, idempotency, and the edge cases teams skip.

⌄

"I tested the API" often means "I sent a valid request and got a 200 back." That's a smoke test, not API testing. Here's what I actually check with Postman and Rest Assured before calling an endpoint covered.

Status codes, properly. Not just the happy-path 200/201, but 400 for malformed input, 401/403 for auth failures, 404 for missing resources, and 409 for conflicts like a duplicate create. An endpoint that returns 200 with an error message in the body instead of an honest status code is a bug, even if the message is technically correct.

Auth and authorization, separately. Does the endpoint reject requests with no token (401)? Does it reject a valid token that belongs to a user without permission for this specific resource (403)? These are two different failure modes, and I've seen both missed independently in the same API.

Pagination edge cases. Page 0, a page number past the last page, a page size of 0 or a huge number, and whether the total count is consistent with what's actually returned.

Idempotency. Calling the same POST/PUT twice — does it create a duplicate record, or does the API protect against that where it should? Same question for a retried request after a timeout.

Data validation at the boundary. Required fields missing, wrong data types, strings that exceed the documented max length, and whether validation errors tell you which field failed.

Response shape, not just response code. Does every success response actually match the documented schema, including fields that are supposed to be present but legitimately null?

On the Availity and ConfluxHR projects, most of the real defects in "tested" APIs weren't in the happy path at all — they were in the auth/authorization split and in what happened on a retried request. The happy path almost always works; it's usually the only thing anyone manually tried.
